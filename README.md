# StudyPlanner — лабораторна робота №1

Курс: Технології створення програмних продуктів.
Тема: Технічне завдання, вибір моделі життєвого циклу, визначення версій, розробка шаблону.

## Структура

| Файл | Призначення |
|---|---|
| `ТЗ.md` | Технічне завдання на проєкт |
| `VERSIONING.md` | SemVer і Git-стратегія |
| `RELEASE_TEMPLATE.md` | Шаблон release notes |
| `CHANGELOG.md` | Історія змін |
| `ACCEPTANCE_CHECKLIST.md` | Чекліст приймання |
| `app.py`, `tests/` | Демонстраційний застосунок і тести |

## Як запустити і перевірити

```bash
pip install -r requirements.txt
pytest                # запуск тестів
flask --app app run   # запуск сервера на http://127.0.0.1:5000
git log --graph --oneline --all   # історія гілок
git tag                           # теги релізів
```

## Вибір моделі життєвого циклу: Agile (Scrum)

Для невеликого проєкту з вимогами, які можуть уточнюватися під час роботи, обрано Agile (Scrum) зі спринтом 1 тиждень. Модель Waterfall тут менш доречна: вона передбачає повне фіксування вимог на початку й не допускає дешевих змін на пізніх етапах. Scrum дозволяє отримувати робочий інкремент щотижня, швидко реагувати на зауваження викладача і природно поєднується з версіонуванням: кожен спринт завершується злиттям фічі в `develop`, а кілька спринтів — релізом із тегом.

Необхідні артефакти: product backlog (список усіх функцій з ТЗ за пріоритетом), sprint backlog (завдання поточного спринту) та Definition of Done (функція виконана згідно з ТЗ, тести проходять, проведено review, оновлено CHANGELOG — див. `ACCEPTANCE_CHECKLIST.md`).

Розклад: спринт 1 — `feature/task-api`, спринт 2 — `feature/task-done`. Наприкінці кожного спринту — sprint review (демонстрація API через `curl`) і retrospective (що пройшло добре, що покращити). Планування спринту — на початку тижня, коротка самоперевірка прогресу щодня.

Ризики: зміна вимог посеред спринту (рішення — переносити зміни в backlog наступного спринту); неточна оцінка обсягу (рішення — малі фічі, що вміщуються в один спринт); відсутність командної комунікації при роботі наодинці (рішення — формальні review і ретроспектива у вигляді нотаток).
